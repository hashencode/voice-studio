# 规则路由与 Electron 第三栏自适应布局开发计划

## 目标与边界

目标有两个，且按顺序交付：

1. AI 在修改代码前能从根入口确定并读取全部适用的现行规范；拆分 `AGENTS.md` 不降低规则的可发现性。
2. Electron 第三栏的页面画布使用全部可用宽度；长文本和个别控件仍可独立控制行宽，窄栏与宽栏都能正常排版。

本计划不改变第二栏现有的默认宽度、240–480px 限值、拖动交互、宽度状态的生命周期，也不改变 Shell 的 Header、Footer、滚动、焦点、导航及空状态策略。不修改 Flutter UI。历史计划和 `docs/solutions/` 作为证据保留，不把它们自动提升为现行规范。

当前工作树已有未提交的 Electron 代码、测试和视觉基准修改。实施时先逐文件查看相关 diff，只在现有内容上增量编辑；不清理、重置或覆盖这些修改。不创建 worktree；若以后确需创建，先按用户给出的项目规则完成具体提案与确认。

## 已确认的产品与规范决定

- 第三栏页面级内容容器占满可用宽度，不用固定或最大宽度把整页居中截断。
- 长段落、单个表单控件等可以单独限制宽度；宽屏下适合并列的信息块按内容关系响应式排布，不机械地让每张卡片或每段文字拉满整行。
- 根 `AGENTS.md` 保留所有不能依赖二次查找的许可与安全门槛；专题细则可以拆出，但必须有确定的读取入口。
- “不会漏读”指可验证的路由覆盖与读取流程，不宣称仅靠 Markdown 能技术上保证模型理解或遵守每条规则。
- 本任务没有视觉验证授权。实现阶段可以做非视觉检查；启动 UI、浏览器、截图、视觉测试和 UI watcher 仍需用户对当次任务明确授权。

## 当前依据

- `AGENTS.md` 目前同时承载 Flutter、Electron 组件与无障碍、视觉文案、验证分级、资源缓存和 watcher 规则。
- `apps/desktop-electron/src/renderer/features/shell/app-shell-frame.tsx` 的第三栏已占剩余空间；`use-context-pane-width.ts` 和 `context-pane-contract.ts` 管理第二栏拖动及主内容最小宽度。
- `apps/desktop-electron/src/renderer/App.tsx` 的 `contentMode`、`contentPadding` 以及各业务页面共同决定第三栏的内边距和通栏例外。
- 设置页、消息详情、录制详情、互联配对页使用页面级 `max-w-*`；音频标题、正文、粘性操作区及播放器使用多处 `max-w-5xl`。这些是拖宽后内容仍被截在中间的直接原因。
- `docs/architecture/electron-audio-context-shell.md` 仍包含早期固定栏宽和 overlay 描述，不能在未核对当前代码前直接作为新布局规范。
- `gmxgy-admin-new` 使用根 `AGENTS.md` 导向 `docs/ai/README.md` 和专题规则；本仓库借鉴入口分层，但避免为局部修改设置过长的无条件必读链。
- Codex 官方说明：启动时自动加载的是从项目根至当前工作目录的 `AGENTS.md` 链；普通引用文档不会因被链接而自动读入。因此从仓库根启动的任务不能只依赖子目录 `AGENTS.md`。参见 https://developers.openai.com/es-419/docs/agent-configuration/agents-md 。

## 实施单元

### U1. 盘点规则，确定单一权威

建立“原条款 → 新归属 → 触发条件”的迁移清单，逐条覆盖当前 `AGENTS.md`。把规则分为：

- 根级常驻：用户本轮提供的 worktree 创建确认规则、现有视觉验证许可、规则读取入口、验证选择原则及跨模块依赖边界。当前仓库 `AGENTS.md` 尚未包含该 worktree 规则，实施时应按用户给出的原意写入，不能把它仅放进专题文档。
- 专题规范：Electron renderer、Flutter UI、验证与构建缓存等仅对相关任务生效的细则。
- 参考资料：系统架构、`CONCEPTS.md`、历史计划和 `docs/solutions/`，通过问题或模块定位后读取。

同一规范只保留一份完整表述；根入口只写触发与路径，不复制专题条款。对现有历史计划中明确要求规则位于根文件的陈述，记录本次用户决定已经改变规范组织方式；不回写历史计划。

**涉及文件：** `AGENTS.md`、现有 `docs/architecture/` 与 `docs/solutions/`（读取与核对）。

### U2. 先实现规则路由，再迁出规则

新增一份可供人和脚本共用的规则索引，建议为 `docs/standards/rules-index.yaml`。每项至少记录适用的路径或任务标签、必读文件和简短原因。新增 `tool/rules_for_change.py`，以预计修改路径和任务标签输出所有适用规则；多模块取并集，无法归类的生产代码路径、失效引用或冲突配置要报错，不能静默返回空列表。

根 `AGENTS.md` 加入强制入口：编辑前确定预计修改路径并运行路由，逐份读取结果；若实际 diff 涉及新路径，再运行一次并补读。规则索引本身是唯一映射来源；不要同时维护另一张手写映射表。根级许可门槛在这个阶段仍留在根文件。

给路由工具添加聚焦测试：Renderer、Main/Preload、Flutter、纯 Dart、文档、跨模块并集、未知生产路径、丢失规则文件。测试要证明匹配、合并和失败行为，不只复述配置内容。

**涉及文件：** `AGENTS.md`，新增 `docs/standards/rules-index.yaml`、`tool/rules_for_change.py`、`tool/test_rules_for_change.py`。

### U3. 原子迁移专题规范

在 U2 的路由和测试可用后，分批建立 `docs/standards/` 下的规范，例如 `electron-renderer.md`、`flutter-ui.md`、`verification.md`、`build-resources.md`。每份采用同一结构：适用范围、必读触发、规则、允许的例外、验证要求、当前权威来源。Flutter 文件继续明确以 sibling `flutter-ui-mobile/DESIGN.md` 和 `DOC.md` 为 UI 权威，并在改 Flutter UI 前读取它们。

每搬迁一组，就核对迁移清单、根入口和路由用例，再删去根文件中的重复细节。保留根级门槛的原意和强度。不要把历史解决方案或过期架构文字复制成现行要求。

**涉及文件：** `AGENTS.md`、`docs/standards/*`、规则路由测试；必要时更新与现行规范相冲突的活跃架构说明。

### U4. 写入第三栏布局规范

在 Electron 专题规范中增加“第三栏布局”小节，规定：

- Shell 第三栏继续占剩余视口宽度，现有第二栏拖动约束不变。
- 页面级画布 `w-full min-w-0`，保留所属页面的合理内边距，不以页面根容器的 `max-w-*` 制造大片未使用空间。
- 阅读型长文本、短表单控件可在自身容器限制行宽；独立卡片和设置分组随可用宽度调整布局，窄宽度下回到单列且不横向溢出。
- 当前明确的通栏页面和空状态 Shell 策略保持原有语义；宽度规范不自动改变 Header、Footer、内容 padding、焦点或导航。
- 新的页面级宽度例外必须在该页面说明用途，不把局部例外推广到整个第三栏。

**涉及文件：** `docs/standards/electron-renderer.md`；根 `AGENTS.md` 只需由路由指向该文件。

### U5. 修改第三栏页面

按页面逐个处理页面级最大宽度，先清除宽度上限，再检查内部布局：

1. 设置页：`App.tsx` 的 `SettingsPanels` 去掉 `mx-auto max-w-4xl`，保持页面 padding；检查设置分组在宽栏中是否适合并列，线性配置流程仍保持自然阅读顺序。
2. 消息详情、录制详情、互联配对：分别检查 `activity-center.tsx`、`capture-workspace.tsx`、`companion-feature.tsx` 的页面根 `max-w-3xl`。让根容器铺满，必要的短文本或表单宽度留在局部元素上。
3. 音频详情：同步处理 `audio-workspace-feature.tsx` 中标题、粘性操作区、标签、正文和播放器的页面级 `max-w-5xl`，避免只有一部分铺满而出现错位；阅读型转写文本可单独控制行长。
4. 检查 `App.tsx` 和 `app-shell-frame.tsx` 的 `contentPadding` / `contentMode`，保留互联历史等现有 edge-to-edge 表现，避免双层 padding 或 Header/滚动行为变化。

只改受宽度规则影响的结构和排版，不顺带迁移组件、重写交互、文案或业务状态。当前未提交修改集中在 `App.tsx`、消息与音频页面，必须在最新工作树上做局部 diff。

**涉及文件：** 上述 Renderer 文件及其最近的稳定交互边界测试（仅在能证明行为回归时调整）。

## 验收与验证

| 阶段 | 验收条件 | 验证方式 |
| --- | --- | --- |
| 规则入口 | 从仓库根开始，给出任一计划修改的生产代码路径，都能得到存在的必读文档；跨模块结果完整去重；未知代码路径失败 | 路由工具单元测试与根目录调用样例 |
| 规则迁移 | 当前 `AGENTS.md` 每条原规则都在根文件或恰当专题规范中找到唯一现行表述；许可门槛未弱化 | 迁移清单、文档 diff、引用一致性检查 |
| 第三栏代码 | 拉宽可用区域时页面画布随之增长；长文本可读；窄栏无横向溢出；音频标题、内容和播放器对齐；现有通栏/空态/Shell 行为不变 | 静态与就近非视觉测试；若获得当次视觉验证授权，再做 UI 检查 |
| 交付 | 仅本计划相关文件新增或修改，原有未提交改动完整保留 | 最终 `git diff` 与状态核对 |

按项目验证分级：计划文档本身只检查 diff 与引用，不运行测试。路由工具落地后运行其聚焦单元测试。Renderer 布局代码落地后，只有得到用户对当次任务的明确视觉验证授权，才从 `apps/desktop-electron` 运行 `bun run check:ui:quick` 和最终 `bun run check:ui`；未授权时报告跳过，不启动应用、浏览器或 watcher。若规范拆分同时改到 Electron Main、Preload 或 shared contracts，再按 `AGENTS.md` 执行对应 `check:code`，并按实际反向依赖扩展验证。

## 风险与处理

- **规则文件拆出后漏读：** U2 必须先于 U3；根入口强制匹配和补读，路由对未知代码路径失败。脚本能验证路由，不能替代 AI 实际理解；交付时列出读取过的文件以供核对。
- **规则重复或冲突：** 使用迁移清单和唯一权威；导航只写触发与指针。历史计划保留为历史，不与现行规范争权威。
- **从仓库根运行时子目录规则未自动加载：** 不将嵌套 `AGENTS.md` 作为唯一入口；根级路由覆盖所有模块。
- **UI 横向展开影响排版：** 不批量替换全部 `max-w-*`；逐页面识别“页面画布”与“局部阅读宽度”，保留 Shell 独立的 chrome 和 contentMode 决策。
- **验证权限限制：** 未授权视觉验证时，静态与单元结果只能证明代码/交互边界，不能声称已观察真实宽屏布局。

## 交付顺序

U1 → U2 → U3 → U4 → U5。U2 的路由用例通过且 U3 的迁移清单核对完成前，不删除根文件的现行细则。U4 的规范生效后才实施 U5，避免代码先于规则定稿。
