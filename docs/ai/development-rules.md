# 开发规则

本文件是本项目核心开发规范的固定入口。根 [AGENTS.md](../../AGENTS.md) 保留授权、工作树和仓库级硬边界；专项正文仍在原标准及业务合同中单点维护。本文件不复制平台样式、测试矩阵或机器路由表。

## 规则发现与实现事实

- 变更前从仓库根对拟改路径运行 `python3 tool/rules_for_change.py <paths>`，按原要求使用适用标签，并读取全部返回文档；完成前按实际路径再次核对。`docs/standards/rules-index.json` 仍是唯一路由表，不在本文件另建路径匹配规则。
- 当前源码和可导入 API 确立实现事实；用户明确决定与现行业务合同按原职责负责。计划、历史审查、来源示例或旧测试不能独立产生新的产品需求。
- 工作树创建、应用身份、资源、组件或其他仓库的操作仍受原授权约束；统一文件名不扩大任务范围，保留其他任务的改动。

## 应用与专项规范

- [PC 端架构与流程](../../apps/desktop-electron/docs/README.md)：只细化本端职责，不能覆盖根授权或跨端合同。
- [App 端架构与流程](../../apps/mobile-flutter/docs/README.md)：只细化本端职责，不能覆盖根授权或跨端合同。
- [标准职责说明](../standards/README.md) 记录各专项的原权威；Flutter / Goo 与 Electron 的组件、布局和运行规则分别适用，不把某一端策略推广到另一端。
- 共享 API、协议及原生合同从 [接口导航](../api/README.md) 查找，字段和状态继续在原合同维护，不复制一套 schema 或在功能包中机械增加 docs。

## 验证、运行与证据

- [验证政策](../standards/verification.md) 仍是检查选择、升级条件、去重和证据边界的唯一详细来源；[资源规则](../standards/build-resources.md) 继续负责适用的缓存、构建与资源操作。纯文档只检查差异和引用，不运行产品测试、分析、构建或 GUI。
- 根 AGENTS 的本次视觉验证授权要求适用于应用、浏览器、模拟器、真机、截图、golden 和视觉测试；没有该授权只选择允许的非视觉检查。资源与设备 watcher 继续遵守原条件。
- 原生、设备、打包、candidate 与发布证据分别解释；旧结果、来源项目通过数或目录调整不替代当前目标验证，不刷新历史验收状态。

## 文档维护

独立专题 Markdown 直接保存在 `docs/` 根目录，按 [文档总导航](../README.md#专题经验) 查找；原元数据、来源与验收范围继续保留。

[AI 导航](README.md) 负责按任务找资料，本文件负责核心开发约束，`standards/` 与应用 docs 保留专题正文。变更具体规则时更新其所属文档和有效引用；冻结来源、历史计划、验收数据与原未验证项保持原位。

## 经验与记忆维护

- 本项目采用按需人工复核，不设置定时复核。用户明确发起复核、相关架构或规范发生变化、不同任务再次遇到同类问题时，只检查受影响条目；普通开发不触发全库整理，也不要求每次任务读取全部记忆。
- 正式规范、架构决定、API 契约、配置和经验文档各自承接对应事实。记忆仅作等待决策的临时候选，不另维护长期规则副本；由文档总导航引用的专题经验按任务相关性查阅，逐篇参与同样的证据、重复与适用范围核对。
- 候选和复核清单默认使用中文，先在当前对话说明未来场景、具体收益、当前证据与已有文件缺口。复核清单逐项列出来源、判断、承接位置或拟补充内容，以及迁移、合并、删除、保留或待决操作。不能只凭文件名或同一主题断言已完整覆盖，也不能只因年代或尚未核实而删除内容。
- 专门保存候选、提升规则、迁移、合并、删除和复发次数更新，均须取得用户对具体批次的明确确认；批准采用本流程不自动授权清理存量。经批准后先补齐正式承接，再在同批清理来源与重复副本，保留原日期、来源、适用范围、验收结论及未验证说明。无新证据不重复提出已拒绝或待决事项，无重要候选时不产生例行记录。
- 仓库根统一保留 `.agents/memories/` 和 `.agents/tmp/`，职责见 [Agent 工作目录](../../.agents/README.md)。经具体批次授权的新候选保存在 `.agents/memories/`；不为补齐目录生成空分类条目，也不另建规则副本。未决定的功能请求保持待决身份，不自动写成产品要求或开始实现。
- `.agents/tmp/` 按日期和任务分目录，放临时脚本、日志及中间核对材料；仅 `.gitkeep` 用于保留目录，其余内容递归忽略，不暂存、不提交，也不强制添加。调试与验收截图仍遵守原 `.artifacts/screenshots/` 规则；正式规范和需要版本管理的验收记录继续在原文档目录维护，不能仅保存在临时目录。
- 复发计数只依据不同任务中同一根因再次出现的独立证据，跟随正式经验条目；重试、重复报错、同一事件的多份记录和重读旧条目不计数。已有规范覆盖仍复发时先核对执行、入口和测试缺口，不自动增加规范。
- 访问资料单独核对约定配置中的承接，不作为经验或规范，不在报告中输出实际值；唯一副本在用户明确决定迁移或删除前保全。其他仓库、组件库、工作树、设备、业务写入和发布的原授权边界继续有效。

### 存量过渡与正式资料

现有记忆与经验正文在具体清理批次获批前保持原样。存量 `PROFILE` / `ACTIVE` 中仍有效且未被当前明确决定替代的项目约束继续生效，相关任务按需核对对应条目；原自动记录、`#promote` 自动提升、每小时整理和自动删除指令不再执行。旧流程中的读取或提升方式由本节接管，不因流程统一擅自撤去有效业务约束。

设计节点、原始来源、架构决策和已完成验收是各自范围内的证据，不因位于记忆或经验目录就批量迁移、删除或改写。跨项目迁入的案例必须保留原项目身份和当前适用范围，不能据历史案例声称当前实现或验收通过；monorepo 在根规则统一管理，按应用职责复核，不为每个包另建一套记忆。
